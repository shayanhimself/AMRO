02 · Sorted by what?

TMDB does not sort by popularity

One request, discover/movie?sort_by=popularity.desc&page=1. Each bar is the popularity value that rank shipped. In a list sorted by that field, every bar would be shorter than the one above it. Six of the nineteen adjacent pairs grow instead.

Amber marks a rank whose value is higher than the rank above it. The gaps are up to 23.5 points, or 15% of the value: not rounding.

The field is a copy, not the key

The parameter is named popularity.desc. The field is named popularity. They are two different numbers. The one you can read lags the one the index sorts on, so a client that re-sorts the page by the field it received produces an order the server never intended.

And TMDB's two popular lists disagree with each other

/movie/popular and discover?sort_by=popularity.desc, requested seconds apart, returned the same twenty ids in a different order:

discover: … 1323244, 1315772, 1375646, 1108427, 1560520 …
popular : … 1323244, 1375646, 1108427, 1315772, 1560520 …

Two surfaces over one index, and they cannot agree on which of two films is more popular.

JustWatch proves it is achievable

popularTitles(sortBy: TMDB_POPULARITY) over fifteen titles is strictly monotonic in the tmdbPopularity it returns:

1027.966  585.875  413.216  318.6  318.6  275.7  260.8
 232.2  230.4  227.7  205.1  197.4  177.3  176.4  173.5

A third party sorting TMDB's number keeps the sort and the number consistent. TMDB, sorting its own, does not. Under POPULAR and TRENDING the same list is monotonic in nothing JustWatch exposes — those two rankings have no readable key at all.

03 · The number, source by source

Thirteen answers to one question

TMDB live

Five list endpoints carry popularity, and so does the detail record.

{
  "id": 1386315,
  "title": "The Runner",
  "popularity": 161.6957,
  "vote_average": 6.054,
  "vote_count": 46,
  "media_type": "movie",     ← only on trending/*
  "softcore": false          ← a second adult flag, on every list item
}

The value is global, not per-list. 25 ids appeared in more than one of the five endpoints in the same minute. Zero carried a different popularity.

And it is not window-scoped, even though the list is. 13 titles appear in both trending/movie/day and trending/movie/week. All 13 carry the identical value in both. The window changes which films are listed and in what order; it does not change the number printed beside them — so the number cannot be what produced the ordering.

What it measures. TMDB documents a “lifetime” score whose daily inputs are votes, views, favourites, watchlist adds, release date, total votes, and the previous day's score. It is recursive: today's popularity is partly yesterday's. That makes it a decayed running total, not a rate, which is why a 40-year-old film can outrank this week's release. Trending is documented only as “calculated quite differently”.

The page cap. movie/popular reports total_pages: 58741 and total_results: 1174803, then refuses page 501. 10,000 of 1.17 million rows are reachable. trending reports total_results: 10000 exactly — that is the cap wearing a count's clothing. total_results also drifts downward within minutes: 1,174,967 → 1,174,819 → 1,174,803 across three requests.

Volatility. Two trending/movie/day requests 2m18s apart returned the same 20 ids in the same order with 0 of 20 values changed. The number is a daily batch, not a live reading.

OMDb spec

One path, /. There is no list endpoint. s= is a title search and its items carry five fields:

{"Title": "…", "Year": "…", "imdbID": "tt…", "Type": "movie", "Poster": "https://…"}

No popularity, no rank, no vote count, no documented ordering. If AMRO needs a browsable list, OMDb cannot supply one.

IMDb live

The seven bulk dataset files have no popularity column. title.ratings.tsv.gz is the closest thing, and numVotes is a lifetime rating count — a fame proxy, not a popularity one, with no list to page.

tconst	averageRating	numVotes

The keyless autocomplete endpoint does carry a popularity rank, and it is the only place IMDb publishes one:

GET https://v2.sg.media-imdb.com/suggestion/t/tt1375666.json
{"d":[{"id":"tt1375666","l":"Inception","rank":129,"y":2010, …}]}

The search variant returns it too, and does not sort by it: Inception 129, The Cobol Job 13,930, a 2016 Inception 105,815, a short 119,246, Jump Right Into the Action 55,398. The licensed datasets omit the number; an undocumented autocomplete endpoint leaks it.

Trakt spec

Eight movie list endpoints, and the cleanest design in the survey. Every one returns a raw count with a stated unit, and the endpoint name says which count did the sorting.

EndpointFieldWhat it counts
movies/trendingwatcherspeople watching right now, last 24h
movies/popularnone—
movies/favorited/{period}user_countusers who favourited it
movies/played/{period}play_countplays, repeats included

movies/collected/{period}collected_countunique collectors
movies/anticipatedlist_countlists it appears on
movies/boxofficerevenueUS dollars, last weekend

played, watched and collected all return the same three counts. Only the sort differs. One call gets all three measures and you pick the ranking:

{ "watcher_count": 66667, "play_count": 109736, "collected_count": 27584, "movie": { … } }

period is daily | weekly | monthly | all.

The only source that ships the denominator

movies/trending sets a response header: X-Trending-User-Count: 1721. 21 watchers out of 1,721 people watching anything is a share you can compute. Every other source gives you a numerator and keeps the denominator.

And movies/popular publishes no number at all. The body is bare movie objects. The docs say popularity there “is calculated using the rating percentage and the number of ratings” — which makes Trakt's popular list a ratings ranking. Trakt documents the formula and withholds the value; TMDB ships the value and withholds the formula.

Keyless requests are refused at the edge (403, Cloudflare interstitial), so this is read from the published blueprint, which itself carries a deprecation banner.

TheTVDB spec

score is format: double, type: number, with no range, no unit and no field-level description. The only explanation is a note at the top of the whole specification:

"score" is a field across almost all entities.  We generate scores for
different types of entities in various ways, so no assumptions should be
made about the meaning of this value.  It is simply used to hint at
relative popularity for sorting purposes.

A vendor stating in its own contract that the number is meaningless except as a sort key. It is the most honest sentence in the survey, and it means the value cannot be displayed, compared across two films, or blended with anything. GET /movies/filter takes sort ∈ score | firstAired | name and requires country and lang, so there is no unfiltered popular list to fetch.

Watchmode spec

GET /list-titles with eight sort_by values, documented as “Popularity options use Watchmode's normalized popularity percentile.”

{"id": 1337513, "title": "Secret in Their Eyes", "imdb_id": "tt1741273",
 "tmdb_id": 290751, "popularity_percentile": 99.421}
A percentile is not a score

It says what fraction of the catalogue a title beats, so the distance between 99.421 and 97.618 is a count of rows, not a difference in audience. Near the top the scale saturates: everything worth showing sits between 99 and 100. It cannot be summed, averaged, or compared across a filtered subset, because the population it ranks against changes.

TitleDetails carries both popularity_percentile and relevance_percentile. On Person, the field named relevance_percentile is described as “Popularity percentile (0-100)” — the spec's own names and descriptions disagree.

Streaming Availability spec

GET /shows/search/filters takes order_by, and the published client enumerates seven values:

original_title   release_date   rating
popularity_alltime   popularity_1year   popularity_1month   popularity_1week

Four popularity windows — the richest popularity model in the survey by a distance. The Show object returns twenty-one fields, and none of them is any of those four. The only score is rating, 0–100, “the average of ratings found online from multiple sources”.

The order, or nothing

The API will rank a catalogue by weekly popularity and then refuse to tell you the weekly popularity of anything in it.

GET /shows/top is a different thing again: “Top shows are determined by the streaming service itself”. It re-serves Netflix's or Prime's own board. Position only, no number, and the methodology belongs to a third party.

Simkl live

Simkl publishes keyless, pre-built trending files, which makes it the only source besides TMDB a client can read here with no credential.

https://data.simkl.in/discover/trending/movies/today_100.json
https://data.simkl.in/discover/trending/movies/week_500.json
https://data.simkl.in/discover/trending/movies/month_100.json
https://data.simkl.in/discover/dvd/releases_100.json

rank is not the list position. The Odyssey is rank: 140 while sitting at position 1 in today, 4 in week and 2 in month. 72 titles appear in all three files and all 72 carry an identical rank in every one. It is a stable global standing, spanning 1 to 73,401, shipped inside a this-week list.

The keyed API refuses without a client id: {"error": "client_id_failed", "code": 412}.

MDBList doc

No popularity number of its own. Its score is a ratings aggregate: “calculated using all the ratings average and with a votes baseline… if the vote count is lower than the baseline, the rating is decreased”.

Its “Popular lists” are other people's lists, re-served:

JustWatch does not expose its own popularity. The Scoring type has no such field, and the validation error says so:

Cannot query field "popularity" on type "Scoring". Did you mean "tmdbPopularity"?

popularityPercentile is rejected outright. The error messages are the schema documentation. The only popularity number JustWatch will give you is tmdbPopularity — TMDB's, mirrored, and stale. jwRating (0–1) exists but is a rating and is not the sort key: under POPULAR the first values run 0.918, 0.833, 0.875, 0.954, 0.966 — no order at all.

The rank is the cursor

JustWatch's pagination cursors are base64 of the 1-based position: MQ== → "1", MTA= → "10". If you want a popularity rank out of JustWatch, decoding the cursor is how you get one. That is the whole ranking: an ordinal, with no value behind it.

Sorting by IMDB_SCORE puts a title with tmdbPopularity: null and jwRating: null at position 1, so the score sorts are unguarded against thin records.

Cinemeta live

Three catalogues, and the manifest labels them differently from their ids: top is displayed as Popular, year as New, imdbRating as Featured. catalog/movie/top.json 307-redirects to cinemeta-catalogs.strem.io and returns 50 items.

Fanart.tv spec

No public list endpoint. /v3/movies/latest returns {"error": "missing api_key or client_key parameter"}. The only count Fanart publishes is likes on an individual artwork, which ranks images, not films.

05 · Gotchas, collected

Everything that will bite a client

Sorting

  • TMDB's sort_by=popularity.desc does not sort by the returned popularity: 6 inversions in 19 adjacent pairs, gaps up to 23.5 points.
  • /movie/popular and discover?sort_by=popularity.desc return the same 20 ids in a different order.
  • Cinemeta's top catalogue is labelled “Popular” and is not sorted by any popularity field it returns.
  • IMDb's suggestion endpoint returns rank and orders by title relevance.
  • Never re-sort a list client-side by the popularity field it came with.

Scales

  • TMDB: unbounded float, recursive on its own previous value. Top 20 span 750 points; ranks 9,980–10,000 span 2.4.
  • Watchmode: a percentile, so a difference is a row count, and it saturates at the top.
  • TheTVDB: a double with a documented instruction not to interpret it.
  • Cinemeta: four scales in one object, one of which is another over 30.
  • Simkl: raw counts, two orders of magnitude below Trakt's for the same films.
  • Trakt and Wikimedia: raw counts with a unit, and for Trakt a denominator in the header.

Types

  • Simkl's drop_rate is a string with a % suffix, unpadded: "0.6%", "1%".
  • Simkl's ids.tmdb is a string while ids.simkl_id is an int.
  • Watchmode's popularity_percentile is nullable.
  • Cinemeta's popularity and popularities are both nullable, and were null together on 3 of 50.
  • JustWatch's cursors are base64 ASCII digits, so the rank round-trips through atob.

Windows

  • TMDB's popularity is identical in the day and the week list. The window orders the list; it does not scope the number.
  • Simkl's rank and drop_rate are identical across today, week and month while watched is window-scoped, so one item mixes both.
  • Streaming Availability indexes four popularity windows and returns none of them.
  • Trakt is the only source where the window is a path parameter and every number in the body is relative to it.

Reach

  • TMDB caps at page 500 (10,000 rows) while reporting total_pages: 58741; trending reports total_results: 10000, which is the cap.
  • Simkl's files stop at 500 items, regenerated hourly at best.
  • Trakt, TheTVDB, Watchmode, Streaming Availability, MDBList and Fanart.tv all need a credential before you see a single row.
  • OMDb and the IMDb bulk datasets have no popularity list at all.

Attribution

  • Simkl requires a visible “Simkl Trending” style title on any surface showing the data, and a User-Agent on the request.
  • Streaming Availability's /shows/top is a streaming service's own board, so the methodology and the licence belong to Netflix, not to the API.
  • MDBList's popular lists are re-served from IMDb, FlixPatrol, TorrentFreak and Trakt, each with its own terms.

06 · For AMRO

What to build

Do not model popularity as a number. Every source that ships one ships a different thing: a decayed lifetime score, a percentile, a watcher count, a page-view count, an ordinal. Storing them all in a popularity: Double throws away the only part that decides whether two of them can be compared.

sealed interface Popularity {
    /** A raw count of people or events, with the window it was counted over. */
    data class Count(val value: Long, val unit: CountUnit, val window: Window) : Popularity
    /** Position in a ranking. The only honest reading of an opaque score. */
    data class Rank(val position: Int, val outOf: Int?) : Popularity
    /** A vendor score with no unit. Displayable never, sortable only within one source. */
    data class OpaqueScore(val value: Double, val source: Source) : Popularity
}
Trust the order

Eleven sources will sort a list and six hand you a number; the two do not agree in any of the six. Take the list in the order it arrives, keep the index, and never re-sort by the field.

Prefer a count

Trakt's watchers with X-Trending-User-Count, and Wikimedia's views, are the only two numbers AMRO could show a user, blend across sources, or defend in review. Everything else can rank, and nothing else can measure.

Keep the source

tmdbPopularity from JustWatch and popularity from TMDB are different fields with the same name, up to 41% apart. A mirror is a separate source.

Treat popularity as stale by default. TMDB's value did not move in 2m18s; Cinemeta was serving a value derived from a TMDB reading 25× out of date; JustWatch was up to 41% off. Cache aggressively and never render a popularity number as if it were current.

For the MVP, one source

TMDB's ordering is coherent within itself and its lists are paginated and cheap. Read trending/movie/day and movie/popular, keep the returned order, keep vote_average and vote_count (which are comparable), and store popularity only as an opaque tiebreaker that never reaches the UI.

07 · Reproducing this

Every finding, as a shell command

TOK=$(grep '^tmdb.readAccessToken=' local.properties | cut -d= -f2-)
H="Authorization: Bearer $TOK"

# TMDB: the sort does not match the field
curl -s -H "$H" "https://api.themoviedb.org/3/discover/movie?sort_by=popularity.desc&page=1" \
  | python3 -c "import json,sys;p=[x['popularity'] for x in json.load(sys.stdin)['results']];\
print([(i+1,p[i],p[i+1]) for i in range(len(p)-1) if p[i]<p[i+1]])"

# TMDB: two popular surfaces, same set, different order
curl -s -H "$H" "https://api.themoviedb.org/3/movie/popular?page=1"
curl -s -H "$H" "https://api.themoviedb.org/3/discover/movie?sort_by=popularity.desc&page=1"

# TMDB: the number is not window-scoped (same id -> same popularity)
curl -s -H "$H" "https://api.themoviedb.org/3/trending/movie/day"
curl -s -H "$H" "https://api.themoviedb.org/3/trending/movie/week"

# TMDB: the page cap
curl -s -H "$H" "https://api.themoviedb.org/3/movie/popular?page=501"
# {"success":false,"status_code":22,"status_message":"Invalid page: … max at 500."}

# Simkl: keyless trending files (User-Agent required)
curl -s  -A "amro/1.0" https://data.simkl.in/discover/trending/movies/today_100.json
curl -sI -A "amro/1.0" https://data.simkl.in/discover/trending/movies/week_100.json | grep -i last-modified

# Cinemeta: four popularities in one object; stremio == moviedb / 30
curl -sL https://v3-cinemeta.strem.io/catalog/movie/top.json \
